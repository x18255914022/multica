# Может ли разработчик (Index Labs / автор репозитория) получить контроль над вашим self-host сервером и агентами?

Вопрос: «сможет ли разработчик в какой-то момент, например после хакерской атаки, использовать мои сервер и агенты как ему будет угодно».

## Короткий ответ

**Через сам код Multica — нет, скрытых бэкдоров не обнаружено.** Но есть **три легальных канала влияния**, которые нужно понимать, и один **косвенный вектор**: если скомпрометирована инфраструктура релизов разработчика (GitHub Releases / Homebrew tap), а ваш демон обновляется из неё — подмена бинарника даст удалённое исполнение кода на ваших машинах. Это главный supply-chain риск.

---

## 1. Что проверено в коде (каналы «звонка домой»)

### Телеметрия self-host (`server/internal/selfhosttelemetry`)
- Жёстко зашитый endpoint `https://telemetry.multica.ai/v1/telemetry/events` (`client.go:11`).
- Отключается полностью переменной окружения `DO_NOT_TRACK` (`cmd/server/main.go:331`, `config.go:31`); при отключении не конструируются ни HTTP-клиент, ни collectors (тест `TestDisabledConfigConstructsNoTelemetryDependencies`).
- Нет редиректов (`CheckRedirect` возвращает `ErrUseLastResponse`), тело ответа никогда не читается — **сервер телеметрии не может ничего «вернуть» исполняемого**. Метрики, не управление.

### Cloud-runtime прокси (`server/internal/cloudruntime`)
- Активируется ТОЛЬКО если оператор сам задал `MULTICA_CLOUD_URL` (`router.go:438`). Без переменной `Enabled()==false`, все вызовы дают `ErrDisabled`.
- Это прокси к управляемому облаку Multica (Fleet/Gateway/billing). В чистом self-host без переменной — мёртвый код.

### featureflag / entitlement
- Фича-флаги читаются из БД/конфига инстанса; внешнего kill-switch, обращающегося к серверам разработчика, не найдено (поиск `license check / expire / kill switch / remote admin` — только тестовые моки).

### Вывод по разделу 1
Протокол daemon↔server pull-based и подписан токенами вашего же инстанса (см. REMOTE_CONTROL.md): **разработчик не может подключиться к вашему серверу или демону «снаружи»** — входящих портов/tunnel нет, аутентификация только на ваши ключи (JWT_SECRET, mdt_/mul_ токены).

## 2. Три легальных канала влияния автора кода

### A. Обновления самого кода (самый сильный канал)
Вы добровольно тянете код разработчика через `git pull` / Docker-образ / GoReleaser / brew. Новый релиз = новый код на вашем сервере. Это нормальный путь для любого open-core проекта, но фактически означает: **доверие к maintainer'у неотличимо от доверия к любому будущему коммиту**. Аудит перед апдейтом (diff, pin версий, сборка из исходников своим CI) — единственная защита.

### B. Самообновление CLI-демона (`internal/cli/update.go`, `internal/daemon/auto_update.go`)
- Автообновление **по умолчанию ВЫКЛЮЧЕНО на self-host**: включается только если server URL == официальный cloud-хост (`config.go:603`, `isOfficialCloudServer` host-only match). Override: `MULTICA_DAEMON_AUTO_UPDATE=false/true`.
- Server-triggered update (`handleUpdate`, heartbeat `pending_update`) требует: запрос от пользователя с ролью owner/workspace-admin (`runtime_update.go: InitiateUpdate → canEditRuntime`), и выполняется на ВАШЕМ сервере — т.е. злоумышленник, взломавший ваш админ-аккаунт, уже имеет контроль и без этой фичи.
- Загрузка бинарника: GitHub Releases API (`api.github.com/repos/multica-ai/multica/releases/tags/...`), **обязательная проверка SHA-256 по checksums.txt GoReleaser**; при отсутствии манифеста — отказ («refuse to replace the binary rather than fall back to unverified install»).
- ⚠️ Ограничения защиты: checksum берётся с того же GitHub-релиза, что и бинарник — **подпись/GPG/sigstore отсутствует**. Компрометация аккаунта организации `multica-ai` или CI GoReleaser позволяет выпустить «валидный» релиз с произвольным бинарником → RCE на всех машинах с демонами, которые обновятся (brew tap — тот же корень доверия).
- ⚠️ Зеркала: env `MULTICA_RELEASE_API_BASE_URL` / `MULTICA_RELEASE_DOWNLOAD_BASE_URL` переопределяют источник — если кто-то контролирует переменные окружения демона, он направляет обновления на свой сервер (checksum тоже придёт оттуда). Держите env демонов под защитой.

### C. Телеметрия (см. п.1) — метаданные об инсталляции, не управление. Ставим `DO_NOT_TRACK=1` и забываем.

## 3. Сценарий «после хакерской атаки на разработчика»

| Вектор | Реализуемо против вашего self-host? | Почему |
|---|---|---|
| Прямой вход на ваш сервер/демоны | ❌ Нет | Нет входящих соединений; аутентификация ключами вашего инстанса |
| Злоупотребление telemetry-multica.ai | ⚠️ Минимально | Только приём POST; клиент не читает ответы, не исполняет; отключается одной env-переменной |
| Подмена релиза (GitHub org / brew tap / GoReleaser CI) | ✅ Да, если вы обновляетесь | Checksum без подписи; единственный реальный RCE-путь. Затрагивает машины с самообновлением (на self-host по умолчанию выкл.) и тех, кто ставит brew/Docker-образы |
| Вредоносный будущий коммит/релиз кода | ✅ Теоретически всегда | Классический supply-chain: решается pin-версий + review diff + собственной сборкой |
| Взлом ВАШЕГО сервера тем же эксплойтом | ➖ Это уже про вашу периметр-безопасность | Уязвимости из SECURITY_AUDIT (JWT_SECRET, path traversal) опаснее любой атаки на разработчика |

## 4. Рекомендации (практический минимум)

1. `DO_NOT_TRACK=1` для сервера; не задавать `MULTICA_CLOUD_URL` без нужды.
2. Оставить `MULTICA_DAEMON_AUTO_UPDATE=false` (дефолт self-host) и обновлять CLI осознанно, pinned-версиями.
3. Собирать образы из исходников своим CI и фиксировать digests, либо верифицировать артефакты GitHub Releases по published digest вручную.
4. Контролировать env daemon-хостов (перечислить `MULTICA_*` в config-as-code; зеркала release-API считать недопустимыми без audit).
5. Если нужен гарантированный «no phone home»: физически вырезать пакет `selfhosttelemetry` (~5 файлов) и `cloudruntime` (~2 файла) — они изолированы, wiring только в `main.go/router.go`; это самый дешёвый cut в проекте (часы, не недели).
6. При компрометации upstream — просто остановить обновление: работающий инстанс сам себя не меняет.

## Итог

Разработчик **не заложил механизма удалённого управления** вашей инсталляцией: все исходящие соединения — pull-протокол к вашему собственному серверу, опциональный cloud-прокси (нужен явный конфиг) и отключаемая телеметрия. Реальная зависимость от него — цепочка поставок обновлений (GitHub Releases/brew без криптоподписей, только SHA-256) и будущее содержимое коммитов. При соблюдении пунктов 1–4 вероятность «использовать серверы как ему угодно» сводится к стандартному для open-source риску подмены релиза, который mitigable pin-версиями и собственной сборкой.
